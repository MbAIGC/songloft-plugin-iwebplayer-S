# 宽屏角标按钮位置与安卓后台播放问题记录

日期：2026-09-12
分支：`dev`

---

## 一、宽屏模式下收藏/倍速按钮遮挡播放模式菜单（已修复）

### 现象

宽屏（分栏）首页里，左下角的「收藏」与右下角的「倍速」两个圆角按钮压在了底部播放控制栏的模式按钮区域上，导致模式菜单（顺序/循环/随机/单曲）被遮住、不好点；手机竖屏没有这个问题。

### 原因

`static/player.js` 的 `placeCornerToolsInActiveSurface()` 在宽屏分栏首页时，会把 `#fp-corner-tools` 整个节点**移动进 `#player-bar`**：

```js
const isSplitHome = window.innerWidth >= 768
    && document.body.classList.contains('split-view-active')
    && !document.body.classList.contains('player-open');
const target = isSplitHome ? playerBar : fullPlayer;   // ← 宽屏塞进控制栏
```

配套 CSS 又把它定位在控制栏内部距底 `54px` 处：

```css
body.split-view-active:not(.player-open) .fp-corner-tools { bottom: 54px; }
body.split-view-active:not(.player-open) .player-bar > .fp-corner-tools { z-index: 3 !important; bottom: 54px; }
```

宽屏下 `--player-height` 被压到 `118px`，控制栏里「模式 / 上一首 / 播放 / 下一首 / 音量」这排按钮正好落在距底约 30~60px 的区间——于是左侧收藏按钮（40px 圆）直接盖住了最左边的模式按钮，`z-index: 3` 又让它画在 `.controls` 之上，所以模式菜单既看不见也点不到。

手机竖屏之所以正常：非分栏时 target 是 `#full-player`，按钮位于播放页底部，也就是控制栏**上方**，天然不重叠。

### 修复

统一成与手机竖屏一致的位置——**始终挂在 `#full-player`（宽屏下即左栏）内，位于控制栏上方**：

1. `static/player.js`：`placeCornerToolsInActiveSurface()` 去掉分栏分支，始终 append 到 `#full-player`。
2. `static/index.html`：
   - 删除 `body.split-view-active:not(.player-open) .player-bar > .fp-corner-tools` 规则；
   - 两个宽屏断点（≥960、768–959）的 `.fp-corner-tools` 规则由 `bottom: 54px` 改为 `bottom: 20px`（即基础位置），并去掉 `z-index: 3` 覆盖（沿用基础 `z-index: 100`）；
   - 删除上一轮为控制栏场景加的 `#fp-corner-speed { margin-right: 10px }`——脱离控制栏后容器 `padding: 0 24px` 左右对称，两侧边距天然一致。

层级关系：宽屏下 `#full-player { z-index: 190 }`、`#player-bar { z-index: 200 }`，因此控制栏（含模式菜单）始终画在角标按钮之上，菜单展开时不会再被挡。

### 验证

- `index.html` 内联脚本语法检查、CSS 花括号配平、`git diff --check` 通过。
- `static/player.js` 为混合行尾文件，本次用**字节级替换**修改，diff 仅 4 增 7 删，无换行污染。

## 二、安卓 App 后台播放：一首歌结束后停止，重新打开 App 又自动播放（问题定位）

### 现象

安卓 APK 在后台运行时，当前歌曲播完后不会自动切下一首，播放就停住了；重新打开 App（回到前台）后又会自动开始播放。

### 代码链路

1. 自动切歌完全由网页端 JS 驱动：

   ```js
   // static/index.html
   audioEl.addEventListener('ended', () => playNextSong(true));
   // → playNextSong() → window.playSong(nextIdx) → 拉流地址 → audioEl.play()
   ```

2. 回到前台时又会「自动播放」，是因为 `static/index.html` 的 `visibilitychange` 处理：

   ```js
   if (document.hidden) {
       window._wasPlayingBeforeHidden = !audioEl.paused && audioEl.currentTime > 0;
       window._interruptedTime = audioEl.currentTime;
   } else if (currentIndex !== -1 && audioEl.paused && window._wasPlayingBeforeHidden) {
       window.playSong(currentIndex, true, window._interruptedTime);   // ← 重新播放同一首
   }
   ```

   也就是「隐藏时在播 → 恢复时若已暂停就重播」这套兜底逻辑在起作用。

3. 原生端（`android/`）现状：

   | 项目 | 状态 |
   | --- | --- |
   | `WAKE_LOCK` 权限 | **没有**（manifest 仅 INTERNET / ACCESS_NETWORK_STATE / POST_NOTIFICATIONS） |
   | 前台服务（foreground service） | **没有**，播放通知只是普通通知（`NotificationManagerCompat.notify`） |
   | `FOREGROUND_SERVICE*` 权限 | **没有** |
   | `webView.onPause()/onResume()` | 未调用（没有 onPause/onResume 覆写） |
   | MediaSession / 锁屏控制 | 有（`MediaSessionCompat` + Bridge 推送状态 + `MediaReceiver`） |
   | 接收「播放结束」的原生处理 | **没有**，完全依赖网页端 `ended` 事件 |

### 判断

歌曲本身能继续在后台播放，说明音频管线正常；**断点在「播完之后的那次 JS 调用」**：`ended` → `playNextSong()` → `playSong()` 全都跑在 WebView 的 JavaScript 里，而 App 进入后台（尤其息屏）后：

- 没有 `WAKE_LOCK`，CPU 进入低功耗/挂起时 WebView 的 JS 任务得不到调度；Chromium 对不可见页面也会做定时器节流与渲染冻结；
- 没有前台服务，App 一旦变成 cached 状态，进程可能被冻结，媒体会话/通知也不再受保护（Android 12+ 的 App Freezing、Android 14 对前台服务媒体的要求）。

于是 `ended` 的处理被推迟到「页面重新可见」（也就是重新打开 App）时才执行——这正好对应「打开 App 又自动播放」。而 `visibilitychange` 的重播兜底会先播回同一首，观感就是「停了，回来又放」。

### 建议修复（原生侧，待确认后实施）

按投入从小到大：

1. **加 `WAKE_LOCK` 权限**（一行 manifest）：让媒体播放/CPU 在息屏时不被挂起，是成本最低的一步。
2. **播放期间持有 `PARTIAL_WAKE_LOCK`**：由 Bridge 的媒体状态推送里 `playing=true/false` 驱动 acquire/release。
3. **把播放通知升级为前台服务**（`FOREGROUND_SERVICE` + `FOREGROUND_SERVICE_MEDIA_PLAYBACK`，API 34+ 必须声明 `foregroundServiceType="mediaPlayback"`）：播放时 `startForeground(媒体通知)`，暂停/停止时退出前台。这样进程不会变成 cached/被冻结，WebView 的 JS 才能在后台继续把下一首接上；锁屏控制的存活也更稳。
4. **网页端兜底增强**（可选，非根治）：记录「隐藏期间是否已经 `ended`」，回到前台时执行 `playNextSong(true)` 而不是重播当前曲，避免恢复时又从头播同一首。
5. **原生侧不接管播放**：保持「网页端播放 + 原生只做媒体会话/控制」的现有架构，不改播放内核。

> 上述原生改动需要真机验证（后台/息屏连续播放、锁屏控制、通知栏按钮），本地只能保证编译通过与逻辑一致性。
