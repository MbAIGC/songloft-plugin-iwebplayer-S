# 宽屏角标按钮遮挡模式菜单 与 安卓后台播放中断 问题记录

日期：2026-09-12
分支：`dev`

---

## 一、宽屏下收藏/倍速按钮遮挡播放模式菜单（已修复，保持按钮原位）

### 现象

宽屏（分栏）首页里，左下角「收藏」、右下角「倍速」两个圆角按钮压住了底部控制栏的模式菜单，展开后菜单被挡、点不到。手机竖屏没有这个问题。

### 原因：层叠上下文把菜单「困住」了

按钮原本挂在 `#player-bar` 内（`bottom: 54px`），而控制栏内部的层叠关系是这样的：

| 元素 | z-index | 说明 |
| --- | --- | --- |
| `#player-bar::before`（毛玻璃底卡） | `0` | 绝对定位 |
| `.player-container`（承载时间/曲名/控制键与弹出菜单） | `1` | ≥960 靠 flex item 的 z-index 生效，768–959 另有 `position: relative` |
| `.fp-corner-tools`（收藏/倍速按钮） | `3 !important` | 直接挂在 `#player-bar` 下 |
| `#mode-popup` / `#volume-popup`（弹出菜单） | `110` | 但位于 `.player-container` **内部** |

关键点：`.player-container` 设了 `z-index: 1`，于是它自己成了一个**层叠上下文**——菜单的 `z-index: 110` 只在这个上下文内部有意义，对外整体就是「第 1 层」。而按钮在 `#player-bar` 这一层是 `3`，`3 > 1`，所以**按钮压在包括菜单在内的整个控制容器之上**，菜单被挡住。

（之前把按钮挪到控制栏外之所以有效，就是因为绕开了这个层级，但那不是正确修法。）

### 修复：解除层叠陷阱，按钮位置不动

1. `.player-container` **不再设 `z-index`**（两个宽屏分支各删一处，768–959 分支同时去掉 `position: relative`），它的子元素（含菜单）于是直接在 `#player-bar` 这一层参与比较：菜单 `110` > 按钮 `3` —— 菜单稳盖在按钮之上。
2. 毛玻璃底卡 `.player-bar::before` 由 `z-index: 0` 改为 **`-1`**：这样容器不再需要 `z-index` 抬层也能把底卡压在内容之下，视觉不变。
3. 进度条 `.progress-container` 保留 `z-index: 1`（与按钮不重叠，无影响）。
4. 按钮相关样式一律保持原样：`bottom: 54px`、`z-index: 3`、`#fp-corner-speed { margin-right: 10px }` 全部不变，**位置与观感与之前一致**。

结果层级（`#player-bar` 上下文内）：底卡 `-1` < 时间/曲名/控制键 `auto` < 角标按钮 `3` < 模式/音量菜单 `110`。

### 验证

`index.html` 内联脚本语法、CSS 花括号配平、`git diff --check` 均通过；本次改动仅 5 行增删（`static/index.html`），`static/player.js` 已还原为改动前状态。

## 二、安卓 App 切到后台后，一首歌播完就停（问题定位）

### 现象（已澄清）

**不是息屏场景**：屏幕保持点亮，只是把 App 切到后台（按 Home / 切到别的应用）。当前歌曲播完后不自动切下一首，播放停住；重新打开 App 又会自动播放。

### 为什么和息屏无关

息屏涉及 CPU 挂起（需要 `WAKE_LOCK`），而后台运行（屏幕亮着）涉及的是另一套机制：**Android 12+ 的 Cached Apps Freezer（缓存应用冻结）+ WebView 渲染进程优先级降级**。

- WebView 默认的渲染进程优先级策略是「不可见时放弃（waive）优先级」（即 `setRendererPriorityPolicy(..., waivedWhenNotVisible = true)` 的默认语义）；
- App 切到后台后不可见 → 渲染进程被标记为可放弃 → 进程成为冻结候选 → 系统冻结该进程 → **WebView 的 JavaScript 停止执行**；
- 音频播放本身不受影响（媒体管线在浏览器进程里，冻结页面时音频继续），所以当前歌曲能正常播完；
- 但「播完自动下一首」是纯 JS：`audioEl.addEventListener('ended', () => playNextSong(true))` → `playSong(nextIdx)` → 拉流 → `play()`。JS 被冻结时这一跳不会执行 → 播放停住；
- 重新打开 App → 进程解冻 → 之前排队的 `ended` / `visibilitychange` 任务立刻补跑 → 于是「又自动播放」；而 `static/index.html` 的 `visibilitychange` 兜底逻辑本身就会在恢复可见且已暂停时重播当前曲：

  ```js
  if (document.hidden) { window._wasPlayingBeforeHidden = ...; window._interruptedTime = audioEl.currentTime; }
  else if (audioEl.paused && window._wasPlayingBeforeHidden) {
      window.playSong(currentIndex, true, window._interruptedTime);
  }
  ```

### 原生端现状（`android/`）

| 项目 | 状态 |
| --- | --- |
| 渲染进程优先级策略 | ❌ 未设置（用的是默认「不可见即放弃优先级」） |
| 前台服务 | ❌ 无，播放通知只是普通 `NotificationManagerCompat.notify` |
| `FOREGROUND_SERVICE*` 权限 | ❌ 无 |
| `webView.onPause()/onResume()` | 未调用（无 onPause/onResume 覆写，这点没问题） |
| MediaSession / 锁屏控制 | ✅ 有（`MediaSessionCompat` + Bridge 推送 + `MediaReceiver`） |
| 原生侧处理「播放结束」 | ❌ 无，完全依赖网页端 `ended` 事件 |
| `WAKE_LOCK` | ❌ 无（仅息屏场景才需要，与本次现象无关） |

### 建议修复（原生侧，待确认后实施）

1. **`webView.setRendererPriorityPolicy(WebView.RENDERER_PRIORITY_IMPORTANT, false)`**（API 26+ 需版本判断）——让 WebView 不可见时也不放弃渲染进程优先级，避免成为冻结候选。这是**针对本现象最直接的一步**，一行代码。
2. **播放期间使用前台服务**承载媒体通知（`FOREGROUND_SERVICE` + `FOREGROUND_SERVICE_MEDIA_PLAYBACK`，API 34+ 必须声明 `foregroundServiceType="mediaPlayback"`）：播放 `startForeground`，暂停即退出。让进程彻底不进入 cached 状态，双保险，同时提升通知/锁屏控制的存活率。
3. 网页端可选增强：记录「后台期间是否已经 `ended`」，回到前台时执行 `playNextSong(true)` 而不是重播当前曲，避免恢复时重复播放同一首。
4. 不建议改动播放内核（保持「网页端播放 + 原生只做媒体会话/控制」的架构）。

> 上述原生改动需要真机验证（后台连续播放、锁屏/通知栏控制）；本地只能保证编译通过与逻辑一致性。
