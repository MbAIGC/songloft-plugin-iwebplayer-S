# iWebPlayer-S 多端适配原则（手机 App / 网页 / 手机竖屏 / 半宽屏 / 宽屏）

> 本文是 **1.3.6 周期"半宽屏沉浸页封面位置"长排查**（1.3.6.05 → 1.3.6.21，共 17 个构建）之后的沉淀。
> **简版见 `AGENT.md`「关键约定 15」**；本文记录完整判据、数据与陷阱，供后续改动与回归时查阅。
> 所有结论都来自**实机运行时数据**，不是推算（教训见文末「陷阱」）。

---

## 一、五个场景怎么划分

适配其实只有**三条互相独立的轴**，把它们组合起来就是全部场景：

| 轴 | 取值 | 由谁决定 | 代码里的判据 |
|---|---|---|---|
| **① 容器** | **App（APK/WebView）** / **网页（浏览器）** | 页面被谁加载 | `html.iwp-app`（引导脚本打标）|
| **② 宽度带** | **手机竖屏** / **分栏（含半宽屏与宽屏）** | 视口宽度 | `matchMedia('(min-width: 768px)')` → `body.split-view-active` |
| **③ 视口高度** | 任意 | 设备/窗口高度 | CSS 变量 `--vh100` |

用户口中的五个场景 = 这三条轴的组合：

| 用户说法 | 容器 | 宽度带 | 典型宽度（CSS px） |
|---|---|---|---|
| 手机竖屏 | App 或网页 | `< 768` | 360–480 |
| **半宽屏** | 通常 App（分屏窗口/半屏） | **分栏** | **实测 1063** ⚠️ 注意不是 768–959，见 §五 |
| 宽屏 | 通常 App（全屏） | 分栏 | ≥ 1200（实测设备上更大）|
| 网页 | 浏览器 | 任意（浏览器宽度自由）| 实测 1179（含地址栏时可视高更小）|
| 手机 App | App | 任意 | `innerHeight ≈ screen.height` |

> ⚠️ **关键认知**：**"半宽屏"不是断点区间**，而是"**分栏布局下窗口较窄**"这种使用状态。
> 代码里的 `768–959` 只是**我们定义的一条带**；实测用户的"半宽屏"窗口宽度是 **1063 CSS px**，落在 `≥960` 里 ✗。
> 因此：**做"仅半宽屏生效"的差异化时，必须用实测宽度确认，不能假设 = 768–959**（1.3.6.16 的返工就源于此）。

## 二、硬性原则（新增/修改任何布局与样式时都适用）

1. **一个判据、一个执行者**（＝`AGENT.md` 约定 12）
   分栏判定**只用** `matchMedia('(min-width: 768px)')`；所有应用（`split-view-active` / 工具栏归属 / `--split-list-top`）**只能**由 `static/index.html` 的 `syncLayout()` 完成。
   **禁止**新增散落的 `innerWidth >= 768`；**禁止**用 `MutationObserver` 观察 `body` 的 class 驱动布局。

2. **宽度带成对出现**（＝约定 13）
   分栏相关规则必须同时在 `768–959` 与 `≥960` 两段出现；改完跑 `npm run audit:breakpoints --strict`，并把新元素登记进脚本的 `CONCERNS` / `Z_TARGETS`。
   *（1.3.5.32/33/35 与 1.3.6.16 的返工都是"某条规则只写在一边"。）*

3. **布局层：App 与网页必须完全一致**
   `html.iwp-app` **不得**用来承载任何**影响布局**的规则（尺寸、间距、显隐、顺序都不行）。
   App 与网页的差别只应该来自**设备本身**（全屏 vs 有浏览器 UI），而不是我们的分支代码。

4. **观感层：允许"仅 App"的微调，但有四条硬约束**
   任何 App 专属的视觉微调必须同时满足：
   - ① 作用域带 `html.iwp-app`（网页端零影响）；
   - ② 用 **`transform` / `opacity` / `filter`** 这类**不参与布局**的属性（不能改变元素占位、不得影响其它列）；
   - ③ 用 **`clamp()`** 设上下限（矮屏不过度、高屏不顶到播放条）；
   - ④ 在 `docs/iWP-S-<大版本>-Dev-记录.md` 里写清"为什么只有 App 需要"。
   当前唯二的两处（1.3.6.19 / 1.3.6.21 定稿）：
   ```css
   /* 首页：封面下移（基准=封面容器自身高度） */
   html.iwp-app body.split-view-active:not(.player-open) .fp-cover-wrapper { transform: translateY(8%); }

   /* 半宽屏沉浸页：封面+歌曲信息整列下移（基准=视口高度，实测 ≈86 CSS px） */
   @media (min-width: 768px) and (max-width: 1199px) {
     html.iwp-app body.split-view-active.player-open .desktop-player-main {
       transform: translateY(clamp(24px, calc(var(--vh100) * 0.08), 140px));
     }
   }
   ```

5. **视口高度统一走 `--vh100`**
   ```css
   :root { --vh100: 100vh; }
   @supports (height: 100dvh) { :root { --vh100: 100dvh; } }
   ```
   原因：浏览器的 `100vh` 是**大视口**（工具栏收起时的高度），不等于当前**可见**高度；App 全屏 WebView 里两者相等。
   不统一 → 同一套 CSS 在浏览器与 App 里位置不同，**浏览器验收会失真**。
   布局相关的 `height/max-height/padding` 一律用 `var(--vh100)`，不要在别处再写裸 `100vh`。

6. **竖屏/窄窗的"手机态"不要被分栏逻辑侵入**
   `< 768` 时分栏关闭（无 `split-view-active`）；`@media (min-width: 600px)` 另有 `body { width: 480px; margin: 0 auto }` 的手机框。
   分栏专属规则请一律写 `body.split-view-active …` 前缀，避免误伤手机竖屏。

7. **绝不用输入框焦点状态驱动布局**（＝约定 10）
   平板浏览器会为保持光标可见而平移页面，叠加 `maximum-scale=1.0` + 全屏锁滚动后无法恢复。要空间就用**按宽度的静态媒体查询**压缩。

8. **量纲纪律：CSS px ≠ 截图物理像素**
   涉及 `vh/dvh/vw/px` 的一切计算只用 **CSS px**；截图是**物理像素**，必须除以 `devicePixelRatio` 才是 CSS px。
   （实测这台平板 DPR ≈ **2.22**，不是 2 —— 用 DPR=2 推算会把 1183 当成 CSS 宽，真实是 ≈1063 ✗。）

9. **验收纪律：用运行时数据，不用推算**
   `☰ → 版本` 曾经临时显示 `视口 / 屏高 / DPR / 是否 App / 位移量`，**正是靠它一次定案**。
   需要判断"某条规则到底有没有生效"时，**优先把数字显示出来**（或 `getComputedStyle(el).transform`），不要靠截图估算。

10. **改完必跑**：`npm test` → `npm run build` → `npm run audit:breakpoints --strict` → `git -c core.whitespace=cr-at-eol diff --check`；改 CSS/HTML 后尤其别跳审计。

## 三、各场景的具体差异清单

| 关注点 | 手机竖屏 `<768` | 半宽屏（分栏窄窗，实测 1063）| 宽屏（分栏 `≥960`，实测更大）| 网页（浏览器）|
|---|---|---|---|---|
| 分栏（三栏/两栏）| ✗ 单栏 | ✓（`split-view-active`）| ✓ | 看浏览器宽度 |
| 左栏 `.full-player` 高度 | 移动布局 | `calc(var(--vh100) - var(--player-height))` | `calc(var(--vh100) - var(--player-height) - 56px - env(...))` | 同左（`--vh100` 保证口径一致）|
| 沉浸页左栏主列 | `display: contents`（**transform 无效** ⚠️）| `align-self: stretch` + `justify-content: center` + `padding-top: 5%`（768–959 段）| 沿用 `≥768` 共用规则 | 同 App，**不加** App 专属位移 |
| 封面下移微调 | 无 | **有**（`html.iwp-app`，≈86 CSS px）| **无**（宽度 >1199 不命中）| **无**（`html.iwp-app` 隔离）|
| `html.iwp-app` | 可能有（若在 APK 里）| 有 | 有 | **必须没有** |
| `--vh100` | `dvh`（回退 `vh`）| 同 | 同 | `dvh`（= 当前可见高度 ✓）|
| 验收重点 | 单栏不溢出、底部不被遮挡 | 封面/信息位置、歌词行数不变 | 与上一版**逐像素一致** | 与 App 观感一致（口径已统一）|

> 首页另有一条**全局**（不分带）的 App 专属位移：`html.iwp-app body.split-view-active:not(.player-open) .fp-cover-wrapper { transform: translateY(8%) }`
> —— 因为首页封面容器自身高度稳定，8% 的量级（≈24 CSS px）用户已验证可接受 ✓。

## 四、`html.iwp-app` 是怎么判定的（纯前端，不需要改 APK）

在 `<body>` 之后的**引导脚本**里（**首帧之前**，避免闪动），四重判据任一成立即打标：

| # | 判据 | 说明 |
|---|---|---|
| ① | `window.Android` | APK 通过 `addJavascriptInterface(new Bridge(), "Android")` 注入 |
| ② | UA 含 `;\s*wv\)` | **WebView 专属**特征，普通 Chrome / Edge 没有 ✓ |
| ③ | UA 含 `iWebPlayer-S-APK` | 备用（将来可自定义 UA）|
| ④ | `innerHeight >= screen.height * 0.94` | App 满屏无浏览器 UI；普通浏览器会少掉地址栏/状态栏 |

另在 `DOMContentLoaded` 再补检一次（幂等）——覆盖"JS 桥/尺寸在首帧后才稳定"的机型。

> ⚠️ 已知风险：④ 可能把**全屏浏览器（F11）/PWA** 误判为 App ✗。若将来发现"网页端也被下移",先查这一条（去掉它即可）。

## 五、本次排查的实测数据（存档，便于同型号设备回归）

| 项 | 实测值 |
|---|---|
| 半宽屏视口 | **1063 × 1078**（CSS px）|
| `screen.height` | 1079 |
| `devicePixelRatio` | **≈ 2.22**（⚠️ 不是 2）|
| 截图物理尺寸 | 2366 × 2400（÷2.22 ≈ 1065 CSS 宽，与 1063 吻合）|
| 生效位移 | ≈ **86 CSS px**（8% × 1078，clamp 未触边界）|
| 生效区间 | `768 ≤ width ≤ 1199` **且** `html.iwp-app` |
| 结论 | 半宽屏命中 ✓ / 宽屏不命中 ✓ / 网页零影响 ✓（用户三轮实测确认）|

## 六、陷阱清单（都真踩过）

1. **`translateY(%)` 的百分比基准是"元素自身高度"**，不是视口 ✗。
   同样写 `8%`：首页（基准=封面容器 ≈300px → ≈24px）看起来刚好；沉浸页（基准=那一列的渲染高度，实际≈内容高）只有 ≈42px，用户反馈"少了"。
   → 需要"跨设备可预测"的位移时，用**视口基准**：`calc(var(--vh100) * X)`。
2. **物理像素 vs CSS 像素**（见原则 8）—— 我曾把 8%×2400 报成 192px，实际 CSS 只有 96px ✗。
3. **断点 ≠ 使用场景**（见 §一 的关键认知）—— "半宽屏"可能落在 `≥960`。
4. **`display: contents` 的元素上 `transform` 无效** —— 手机态（`<768`）下 `.desktop-player-main` 是 `display: contents`，
   所以任何针对它的位移在手机竖屏下**什么都不会发生**（不报错、也不生效）。
5. **`transform` 不参与布局** —— 位移过大会遮挡/被 `overflow: hidden` 裁剪、或顶到底部播放条；务必 `clamp()`。
6. **`dvh` 在旧 WebView 可能不支持** —— 必须保留 `100vh` 回退（我们的 `@supports` 写法已覆盖）。
7. **子资源是 `immutable, max-age=1年`** —— 新增图片/字体等子资源必须纳入 `inject-version-hashes.mjs`（＝约定 5）。
8. **别用浏览器当唯一验收环境** —— 浏览器有地址栏/工具栏，可见高度与 App 不同；口径已由 `--vh100` 统一，但仍建议**以 App 实机截图为准**。

## 七、新增/修改一条适配规则时的检查清单

- [ ] 这条规则属于哪条主轴？（容器 / 宽度带 / 视口高度）
- [ ] 若是布局：两段分栏带是否**成对**写了？`audit:breakpoints --strict` 过了吗？新元素登记进 `CONCERNS` 了吗？
- [ ] 若是"仅 App"：是否带 `html.iwp-app`？是否**只用不参与布局**的属性？是否 `clamp()` 有边界？
- [ ] 是否误伤手机竖屏（`<768`，无 `split-view-active`）？
- [ ] 是否误伤网页端（浏览器里 `html.iwp-app` 必须为假）？
- [ ] 是否用了 `var(--vh100)` 而不是裸 `100vh`？
- [ ] 量纲是否都是 **CSS px**？
- [ ] 有没有"把数字显示出来"再验证（而不是靠截图估算）？
- [ ] 已在本大版本记录文档里补条目、并同步索引表了吗？
